**Назначеие**

Сервис генерирования GIF картинок с псевдослучайным содержимым, которое зависит от 1 параметра

**Установка и инструментарий**

Недостающие сторонние модули нужно устанавливать через pip:
`pip install jinja2 werkzeug mysql-connector-python Pillow python-dotenv`
(на другой машине этот список может быть быть как больше, так и меньше)

1. jinja2 - шаблонизатор для генерации HTML страниц - https://jinja.palletsprojects.com/en/stable/
2. werkzeug - WSGI toolkit - https://werkzeug.palletsprojects.com/en/stable/
3. mysql.connector - соединенеие с MySQL для питона - https://dev.mysql.com/doc/connector-python/en/quick-installation-guide.html
4. Pillow - генерирование изображений - https://pillow.readthedocs.io/en/stable/
5. python-dotenv - чтение .env файла из корня проекта

**БД**

До запуска нужно создать БД в локальном MySQL.
Параметры доступа к БД задаются в файле .env в корне проекта.
Чтобы его создать, скопируйте .env.example в .env и укажите свои логин и пароль.
Файл для инициализации БД (init.sql) лежит в корне проекта.

**Запуск**

Команда запуска веб сервиса
`python src/anno.py`
Стартует на порту 5555 и слушает все IP (0.0.0.0).
http://localhost:5555/ - ведет прямо на админку.
http://localhost:5555/testing_get - страница для тестирования GET запросов
http://localhost:5555/testing_post - страница для тестирования POST запросов
Если предварительно залогиниться в админку, то тестовые страницы будут открываться для того же юзера.
Если не логиниться, то будет использован юзер с id=1. Его зовут test.
Это реально существующий юзер из БД.
Просто у него неменого особенная роль.
Считается, что его логин и пароль известны всем. 
При генерировании тестовых страниц эти значения логина и пароля передаются шаблонизатору, если нет другого юзера с валидной сессией. 

**Использование**

До того, как пользователь сможет начать получение GIF картинок, он должен пройти аутентификацию в веб сервисе.
Это не то же самое, что аутентификация на веб интерфейсе программы. 
Это отдельный POST запрос к веб сервису.
Клиент передает свой логин и пароль и получает аутентификационный токен, сгенерированный для определенного user id.
В дальнейшем из токена может быть выделен этот user id для проверки, кому принадлежит токен.
Токен сохраняется клиентом в глобальной переменной `window.gifMakerAuthToken`.
В дальнейшем он используется для генерации самих GIF файлов.
*Важная особенность* : секрет для генерации токена генерируется случайным образом при запуске веб сервиса.
Следовательно при перезапуске веб сервиса все выданные ранее аутентификационные токены станут невалидными.
Можно исправить заменой рандома на фиксированную секретную строку. А можно и не исправлять.

Юзер админки и юзер веб сервиса - это физически один и тот же юзер в БД.
Но процедура аутентификации используеться разная.
Аутентификация в админке создает запись в БД в таблице admin_sessions. Запись может устаревать.
Аутентификация в самом веб сервисе создает token, который не сохраняется в БД, но может быть проверен сам по себе. 

Если есть аутентификационный токен, можно делать реальные запросы на генерацию анимированных картинок.
Есть 2 возможности сделать это:
1. POST запрос. Телом запроса является JSON. Ответ - тоже "application/json".
Одно из полей ответа - это URL, по которому лежит результат.
Сам результат потом нужно подтянуть на страницу отдельным запросом или сохранить где-то как URL.
Он лежит в отдельной публичной папке веб приложения. 
Имя результата достаточно случайно. Например
`/static/1/1790245945_1_d41d8cd98f00b204e9800998ecf8427e.gif`
/1/ - подпапка, имя которой содержит целочисленный id юзера
1790245945 - unixtime. Время генерации файла
1 - id шаблона, который использовался для генерации
d41d8cd98f00b204e9800998ecf8427e - md5 хеш от зерна, которое использовалось при генерации
Поэтому можно не опасаться, что один юзер перебором найдет файл, которые генерировал другой юзер.

2. GET запрос. Тела запроса нет. Параметры запроса - это параметры прямо в URL. Ответ - "image/gif".
Такой URL можно прямо использовать в качестве значения атрибута src у элемента <img>  
`let url1 = "http://localhost:5555/g?token=__TOKEN__&t=123&template=1";`
`jQuery('#demo1').attr('src', url1.replace('__TOKEN__', window.gifMakerAuthToken));`

Каждый запрос создает запись в БД. Это сделано для кеширования результата.
Если юзер А создает GIF картинку вида B c зерном C, то запись об этом сохраняется в БД.
Повторный запрос от А на картинку вида B c зерном С вернет ранее сохраненный файл, 
а не будет запускать генерацию GIF картинки заново. Это существенно ускоряет сервис.
В качестве обходного пути запрос на генерацию GIF файла имеет специальный флаг, 
который не дает веб сервису использовать кеш и всегда создает новый GIF файл. 

**Тестирование**

Генераторы (src/gen_* файлы) в тестовых целях могут запускаться сами по себе.
Например так `python src/gen_f.py`
Считается, что в этом случае их запускает юзер с id=0 (это не 'test', у которого id=1). 
Юзера с id=0 не существует в БД.
Но в публичном каталоге есть подпапка для результатов этого юзера.
Дефолтные аргументы для тестовой генерации гифки находятся в самом низу .py файла-генератора.
Все промежуточные кадры сперва создаются в полдпапке /frames/
Все результаты создаются в подпапке /static/0/
Каждый генератор может запускаться без параметров. Если они есть, то они опциональны.

Запуск всех тестов (из корня проекта):
`python -m unittest discover -s tests -v`
Запуск одного теста из одного файла (из корня проекта):
`python -m unittest tests.test_gen_f.TestFGenerator.test_make_2_different_gifs_type_1 -v`
В этом случае генераторы тоже работают так, будто их запускал юзер с id=0

**Дальнейшее развитие**

Дальнейшее развитие проекта связано с увеличением количества GIF генераторов и их параметров,
которые пользователь может изменять через веб интерфейс.
